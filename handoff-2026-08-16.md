## What shipped this session

### 1. Public frontend — built and deployed live
`public/index.html` — single-file PWA (Leaflet map, inline CSS/JS, no build step). Live at:
- **Production:** https://elysiumwatch.pages.dev
- Cloudflare Pages project name: `elysiumwatch`, production branch: `main`

Features:
- Map centred on the actual neighbourhood (coords set in `DEFAULT_CENTER` in the JS). Last map position (centre + zoom) saved to `localStorage` and restored on next visit.
- **Tap-to-report flow**: tap anywhere on the map drops a pin and opens an inline confirm popup ("Report something here?"), drag to reposition before confirming. Only after "Yes, continue" does the message/photo form (bottom sheet) open.
- **Address search** via Nominatim (OpenStreetMap's free geocoder, no key/card) — debounced 500ms, selecting a result centers the map and drops the draft pin there too.
- **Report categories**: Suspicious activity, Fire, Flood, Electrical fault, Water supply fault, Other. Electrical/Water show a conditional, optional municipal reference-number field.
- **"When did this happen"** datetime field, defaults to now, editable (separate from `created_at` submission timestamp).
- **Name field**, optional, persisted in `localStorage` (not a login system) for future submissions on the same device.
- Approved reports render as category-colored pins with popups (message, time, ref nr, incident time, photo if present).
- PWA manifest + service worker shipped (`public/manifest.json`, `public/sw.js`) — fully installable. Icons live at `public/icons/icon-192.png` and `public/icons/icon-512.png` (blue shield, generated with cairosvg from SVG).

### 2. Worker backend — built and deployed live
`worker/index.js`, deployed as `neighbourhood-watch-api`. Live at:
- `https://neighbourhood-watch-api.morneydeetlefs.workers.dev`

Routes (all under `/api`):
- `GET /api/reports` — approved reports only, public, no auth
- `POST /api/reports` — creates a report with `status='pending'`, then fans out a Web Push notification to all subscribed admin browsers (fire-and-forget via `ctx.waitUntil`)
- `POST /api/reports/image-upload` — uploads a photo to B2, returns `{ image_key }`
- `GET /api/reports/:id/image` — proxies an image from B2, only for reports with `status='approved'`
- `GET /api/admin/reports` — pending reports queue (ADMIN_KEY required)
- `POST /api/admin/reports/:id/approve` — atomically approve (ADMIN_KEY required)
- `POST /api/admin/reports/:id/reject` — atomically reject with optional reason (ADMIN_KEY required)
- `GET /api/admin/reports/:id/image` — proxies image for any status (ADMIN_KEY required)
- `GET /api/admin/reports/history` — approved/rejected history (ADMIN_KEY required)
- `POST /api/admin/push-subscribe` — saves a browser push subscription to D1 (ADMIN_KEY required)
- `POST /api/admin/push-unsubscribe` — removes a push subscription by endpoint (ADMIN_KEY required)

B2 integration is hand-rolled against B2's **native API** (not S3-compatible) using plain `fetch` + Web Crypto (SHA-1 content hash) — no npm dependency. Auth token cached in module scope (~23h).

VAPID push signing is also hand-rolled using Web Crypto (ECDSA P-256 JWT) — no npm dependency. Same pattern as B2 auth.

### 3. D1 database — schema loaded on remote
`db/schema.sql` — `reports` table.
`db/schema-push.sql` — `push_subscriptions` table (added this session).

`push_subscriptions` columns: `id`, `endpoint` (UNIQUE), `p256dh`, `auth`, `created_at`.
Indexed on `created_at`. Upsert pattern on subscribe (endpoint conflict updates keys).
Stale subscriptions (410/404 from push service) are cleaned up automatically during fan-out.

- D1 database: `neighbourhood-watch-db`, binding `DB`

### 5. Admin console — `public/admin/`
`public/admin/index.html` — single-file admin console. Live at:
- **Production:** https://elysiumwatch.pages.dev/admin/

Features:
- Login screen with `ADMIN_KEY` passcode, persisted in `sessionStorage`
- Moderation queue: pending reports with approve/reject (with optional rejection reason)
- History section: approved/rejected reports with filter (All / Approved / Rejected) and re-review capability
- Mini OpenStreetMap embed per card, photo lightbox, category pills
- **🔔 Push notification toggle** in header — subscribe/unsubscribe this browser for Web Push alerts
- Toast notifications, card slide-out animations
- **Installable as a PWA** — `public/admin/manifest.json` (amber theme, name "EW Admin"), icons at `public/admin/icons/` (amber shield with lock badge). Separate branding from the public PWA so both can be installed side-by-side on the home screen.

### 6. Web Push notifications — fully live
`public/admin/sw.js` — admin service worker (separate from the public PWA's `public/sw.js`).

How it works:
- Admin logs in, clicks "🔔 Enable alerts" — browser prompts for notification permission
- On grant, `PushManager.subscribe()` creates a subscription using the VAPID public key
- Subscription (`endpoint`, `p256dh`, `auth`) POSTed to `/api/admin/push-subscribe` → saved to D1
- When a resident submits a report, `POST /api/reports` fans out a push to every stored subscription via `ctx.waitUntil(fanOutPush(...))`
- Each admin browser receives the push, service worker shows an OS notification (category emoji + title + body)
- If the admin tab is open, service worker also `postMessage`s `{ type: 'PLAY_ALERT' }` to the tab
- Tab plays a two-tone Web Audio ding-dong beep (no audio file — generated with Web Crypto oscillators)
- AudioContext is primed on first user interaction (login tap/click) to satisfy browser autoplay policy

VAPID keys:
- Generated with a Node one-liner (see README), set as Worker secrets `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`
- Public key **also hardcoded** in `public/admin/index.html` at `const VAPID_PUBLIC_KEY = '...'`
- ⚠️ Every time a new `admin/index.html` is generated in chat, the public key must be re-pasted manually — the chat session does not retain it
